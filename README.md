# nara — 나라장터 품목 수집·가격비교표 생성

현재 촬영용 변경으로 지지대 개수 검사를 임시 중지했습니다. 미확인·개수 차이·지지대 속성 충돌은 후보 탈락 사유가 아니며, 규격·재질·가격 등 나머지 검사는 유지합니다. 아래의 지지대 일치 설명은 정상 운영 정책입니다. 복원은 `core/comparison.py`의 `CHECK_SUPPORTS = True`로 변경한 뒤 API·워커 재시작(컨테이너는 재빌드)이 필요합니다. 기존 보류 작업은 새 수집으로 다시 비교해야 합니다.

나라장터 종합쇼핑몰의 공개 조회 응답을 받아 업체별 품목을 비교하고, 상품 사진을 포함한 Excel을 만드는 Python CLI입니다. 현재 기본 사용 방식은 **터미널에서 `uv run`으로 실시간 조회 → 파일 저장**입니다. 비교표 생성에는 Docker, 운영 DB, LLM API 키가 필요하지 않습니다.

웹에서는 **조건 입력 → Prefect 수집 → 후보 검토 → Excel 생성** 순서로 작업할 수 있습니다. Figma Furrow 화면을 바탕으로 만든 FastAPI 웹이며, 비교 결과는 DB 대신 JSON 파일로 보존합니다. 웹 작업에는 Prefect 서버와 프로세스 워커가 필요합니다. 설치·실행·API는 [웹 실행 안내](docs/web-operations.md)를 참고하세요. 기존 CLI는 그대로 사용할 수 있습니다.

검토 화면의 **다른 후보 찾기**는 선택한 경쟁사 후보 한 개만 재검색합니다. 포함할 재질을 선택적으로 입력할 수 있으며, 다른 후보·품목과 기존 가격·규격 조건은 유지합니다. 교체 후 가격순으로 다시 정렬하고 Excel을 재생성하세요.

웹 전체를 Docker로 실행하려면 `docker` 폴더에서 `docker compose -p nara-web-deploy -f compose.web.yaml up -d --build`를 사용합니다. 인증값을 설정한 `.env`가 필요하며 Nginx 진입점은 `http://127.0.0.1:8080`입니다. 품목 응답용 Redis는 Prefect 큐와 분리하고, 작업 파일은 볼륨에 보존합니다.

## 1. 처음 실행하기

저장소 루트에서 실행합니다. Python은 `>=3.12,<3.13`을 사용하며 버전과 의존성은 `.python-version`, `pyproject.toml`, `uv.lock`으로 관리합니다. `uv`가 설치되어 있어야 합니다.

```sh
cd /Users/ijongseung/nara
uv sync --locked
uv run python compare_file.py --help
```

다른 위치에 복제했다면 `cd` 경로를 해당 저장소로 바꿉니다. `.venv`를 직접 만들거나 활성화할 필요는 없습니다.

먼저 품목 3개만 확인합니다.

```sh
uv run python compare_file.py --company "지피코리아" --keyword "안내판" \
  --limit 3 --top 3 --workers 2 --out comparison-test.xlsx
```

이 명령은 기준 업체 품목을 최대 3개 조회하고, 품목마다 경쟁사 최대 3개를 골라 비교표를 만듭니다. **유효한 경쟁사가 3개 있다는 뜻은 아닙니다.** 비교표의 출력 폴더는 자동으로 생성하며 기존 파일은 덮어쓰지 않습니다. `--out "./output/비교표.xlsx"`, `--out "~/Downloads/비교표.xlsx"`처럼 지정할 수 있습니다. 재실행할 때 새 파일명을 지정합니다.

입력 `.xls`, 수집 결과 파일, 빈 Excel 템플릿을 미리 준비할 필요는 없습니다. 프로그램이 워크북을 만듭니다.

## 2. 목적별 명령어

| 목적 | 명령 | 결과 |
|---|---|---|
| 업체별 최종 비교표 | `uv run python compare_file.py --company "업체명" --out comparison.xlsx` | 업체별 시트, 품목별 비교 블록, 가격·사진 |
| 원본 품목 목록 수집 | `uv run nara collect --keyword "안내판" --limit 500 --out catalog-live.xlsx` | 수집정보와 실시간 품목 목록 |
| 원본 JSON 보존 | 위 `collect` 명령의 `--out catalog-live.jsonl` | 첫 줄 메타데이터, 이후 품목별 원본 |
| 기존 품목등록결과로 비교표 | `uv run python compare_file.py "품목등록결과.xls" --out comparison-from-file.xlsx` | 파일의 희망가를 기준으로 비교 |
| 제출용 양식 변환 | `uv run python format_convert.py "품목등록결과.xls" --out negotiation.xlsx` | 협상품목리스트 |

`collect` 결과는 최종 경쟁사 비교표가 아닙니다. `compare_file.py`는 필요한 조회를 직접 수행하므로 비교 전에 `collect`를 실행할 필요가 없습니다. 수집 결과 파일을 비교 명령이 자동으로 읽는 구조도 아닙니다.

### 업체 전체 또는 여러 업체 비교

```sh
uv run python compare_file.py --company "지피코리아" --keyword "안내판" \
  --limit 0 --out comparison-all.xlsx

uv run python compare_file.py --company "지피코리아" --company "경무기업" \
  --keyword "안내판" --limit 3 --top 3 --out comparison-companies.xlsx
```

- `--limit 0`은 해당 검색 조건의 업체 품목 전체를 요청합니다. 업체 조회의 안전 상한은 10,000건이며, 결과가 이를 넘으면 일부를 전체처럼 출력하지 않고 종료합니다. 일부만 원하면 `--limit 10000`처럼 명시합니다.
- 법인격·공백을 정리한 이름이 일치하는 제조업체만 기준 품목으로 선택합니다. 제조업체명이 없으면 계약업체명을 사용합니다. 사업자번호 기반의 법인 동일성 인증은 아닙니다.
- `--keyword`는 기준 업체의 조회 품목을 제한합니다. 경쟁사는 품명으로 검색하며, 용도 문구는 순위에만 반영합니다.
- 여러 업체를 지정하면 업체마다 시트를 만들고, 지정한 업체들은 서로 경쟁사 후보에서 제외합니다.
- 기준 업체의 원천 조회 한도 적용 후 업체명을 대조하므로 실제 포함 품목 수가 `--limit`보다 적을 수 있습니다.

### 기존 동일단가 비교

```sh
uv run python compare_file.py --company "지피코리아" --keyword "안내판" \
  --limit 3 --exact-price --fallback-band 0 --out comparison-exact.xlsx
```

`--exact-price`는 같은 단가의 후보를 검색합니다. **규격 각 변 ±10% 등 필수 조건과 확인 필요·대안 후보 구분은 동일하게 적용합니다.** 방향 수 일치는 `--same-direction`을 켰을 때만 검사합니다.

`--exact-price`에서 조건을 충족한 동일 가격 후보가 하나도 없을 때만 가격대를 넓히려면 다음처럼 실행합니다.

```sh
uv run python compare_file.py --company "지피코리아" --keyword "안내판" \
  --limit 3 --exact-price --fallback-band 0.3 --out comparison-price-band.xlsx
```

동일단가 모드에서 `--fallback-band`를 생략하면 기본값은 `0.3`입니다. 재검색에서도 구조·규격 검사를 유지하며, 기준보다 높고 상한 가격대 이내인 후보만 선정합니다. 정확히 같은 단가만 원하면 반드시 `--fallback-band 0`을 지정합니다. 근사 후보에는 `(근사)`가 붙습니다. 동일단가 후보가 일부라도 있으면 부족한 칸을 가격대 후보로 추가 충원하지 않습니다.

### 기존 품목등록결과 파일 사용

```sh
uv run python compare_file.py "품목등록결과.xls" --limit 3 --out comparison-from-file.xlsx
uv run python format_convert.py "품목등록결과.xls" --out negotiation.xlsx
```

비교 입력은 `.xls`이며 헤더명을 기준으로 읽습니다. 기준 가격은 파일의 `희망가(부가세포함)`입니다. 업체 조회 모드의 기준 가격은 사이트의 `ctrtUprc` 계약단가입니다. 두 가격의 성격은 다릅니다.

`--company`와 입력 파일은 함께 지정할 수 없습니다. `--keyword`는 `--company` 전용입니다. 입력 파일에 원천 이미지 URL이 없으면 기준 품목 사진이 채워지지 않을 수 있습니다.

### 주요 비교 옵션

| 옵션 | 기본값 | 의미 |
|---|---|---|
| `--company` | 없음 | 조회 업체명. 여러 번 지정 가능 |
| `--keyword` | 빈 값 | 기준 업체 품목 조회 범위 제한 |
| `--limit` | `0` | 업체별 기준 품목 조회 한도. `0`은 전체 요청, 업체 모드는 최대 10,000건 |
| `--top` | `3` | 기준 품목 하나당 서로 다른 경쟁사 수의 상한 |
| `--workers` | `8` | 품목별 경쟁사 매칭 스레드 수. 기준 업체 수집은 최대 4개 프로세스 사용 |
| `--out` | `가격비교표.xlsx` | 새 출력 파일 경로 |
| `--exact-price` | 꺼짐 | 동일단가 검색. 규격 등 필수 검사와 후보 구분은 유지 |
| `--same-direction` | 꺼짐 | 선택 조건. 켜면 알려진 1방향·2방향 등의 방향 수도 일치해야 함 |
| `--fallback-band` | 기본 비교 `0`, 동일단가 모드 `0.3` | 동일단가 후보가 전혀 없을 때 가격대 재검색. 허용 범위 `0..1` |
| `--mode` | `suggest` | 추천 모드. `shadow`·`auto`는 별도 원천·정책·release 필요 |

`--top`을 늘려도 조건에 맞는 상품이 없으면 후보가 추가되지 않습니다. `--workers`는 요청 제한을 해제하는 옵션이 아닙니다.

## 3. 기본 보강 비교 규칙

비교 CLI는 다음 순서로 처리합니다. 동일단가 검색과 진단 SQLite 입력에서도 구조·규격 검사를 적용합니다.

1. **기준 품목 추출:** 속성 이름과 코드 정의를 읽어 규격·재질·용도를 복원합니다. 특정 업체·상품 번호나 속성 코드 위치를 고정하지 않습니다.
2. **후보 조회:** 품명으로 검색하고, 기준 가격보다 높은 후보를 선정합니다. `방향안내` 같은 용도 문구를 검색 필수어로 넣거나 문구 불일치로 제외하지 않습니다. 용도 유사도는 순위에만 반영합니다. 응답 가격은 코드에서 재검사합니다. 후보 풀은 품목당 최대 500건이며, 동일 가격 검색은 `--exact-price`로 선택합니다.
3. **필수 검사:** 규격 각 변 ±10%, 선택한 가격 조건, 동일 제품·기준 업체 제외를 유지합니다. 양쪽에 명시된 품명·세부품명번호·형상이 다르면 제외합니다. 방향 수는 `--same-direction`을 켰을 때만 필수 검사합니다. 지지대 검사는 현재 촬영용으로 중지했습니다.
4. **선택적 상세 보강:** 부족한 속성을 품목당 `max(8 × --top, 24)`개까지 상세 조회합니다. 한도를 넘겨도 필수 규격 등이 확인된 후보는 확인 필요로 남깁니다. 규격 미확인 후보는 ±10%를 검증할 수 없어 제외합니다.
5. **구분 후 선정:** 조건 충족 → 확인 필요 → 대안 후보 순으로 부족한 칸을 보충합니다. 분류·형상·재질 정보가 없거나 표시면·설치·발광·반사 정보가 한쪽에 없거나 충돌하면 확인 필요입니다. 표시면·설치·발광·반사 방식이 명확히 다르면 대안 후보입니다. 각 그룹 안에서는 재질 일치 수준, 작은 규격·높은 가격, 유사도 순으로 경쟁사당 하나를 고릅니다.
6. **Excel 배치:** 선정된 경쟁사 열을 **기준 업체 오른쪽에서 왼쪽→오른쪽 가격 오름차순**으로 놓습니다. 확인 필요·대안 후보는 업체명 옆에 표시하고 셀 메모에 사유를 남깁니다. 웹 검토에도 동일 구분과 검색·탈락 집계를 표시합니다.

### 재질

- 재질 원문과 여러 성분을 보존합니다. 알루미늄 전용 로직이 아닙니다. 스테인리스·목재·강재·수지·유리·석재 등을 처리하며 미등록 명칭도 원문으로 남깁니다.
- 우선순위는 정규화된 재질 명칭 일치 → 계열 일치 → 기준 재질을 포함하는 혼합 재질입니다.
- 양쪽에 등급이 기재되어 있고 서로 다르면 제외합니다. 한쪽에 등급이 없으면 동일 등급으로 추정하지 않습니다.
- 일반 유리와 강화유리, 구리와 황동 등을 같은 재질로 바꾸지 않습니다.
- 재질 속성 코드와 합금 등급은 별개입니다. 예를 들어 `ATTR...`는 속성 식별자이고 `STS304`, `A5052-H32`는 원문에 기재된 등급입니다.
- 같은 계열·같은 명칭이라는 판정은 품질·강도·제품 동등성 인증이 아닙니다.

### 규격·지지대·방향

**가로와 세로 각각 기준 대비 ±10% 이내**가 필수 조건입니다. 단위를 mm로 환산하며 면적이나 두 변의 평균으로 대신하지 않습니다. 기준이 600×150mm이면 가로 540~660mm, 세로 135~165mm입니다. 680×140mm는 가로 차이가 13.3%여서 제외합니다.

지지대 수는 **0개·1개·2개·미확인**을 구분하며 양쪽 개수가 일치해야 합니다. 원천 속성의 `지지대수`·`다리 개수` 등이나 규격명에 명시된 수량·미포함 정보를 읽습니다. 특정 업체·상품번호별 개수를 하드코딩하지 않으며, 양면·고정식·지지대 높이만으로 개수를 추정하지 않습니다. 기존 `.xls` 입력에서도 해당 이름의 열을 읽습니다.

현재 실행 코드는 사진을 내려받아 Excel에 넣으며 **사진 속 다리 개수를 자동으로 인식하지는 않습니다**. 개발 중 Codex가 사진을 보고 판단한 결과도 실행 시 사용할 데이터로 간주하지 않습니다. 사진에서 개수를 복원하려면 별도 Vision API나 모델을 연결하고 정확도를 검증해야 합니다. 원천과 상세 조회로도 개수가 확인되지 않으면 비교를 보류합니다.

필수 조건을 통과한 후보 중에서는 **가로·세로가 모두 기준 이하이고 하나 이상 더 작으며, 가격은 기준보다 높은 경우**를 우선합니다. 이 우선 조건을 충족하지 않으면 회사명 셀 메모에 `작은 규격·높은 가격 조건 미충족`을 기록합니다. 규격 검사는 판면 두 변에 대한 것이며 지지대 높이·두께·전체 구조의 동등성까지 보증하지 않습니다.

`1방향안내`와 `양면`은 다른 속성입니다. `방향안내`처럼 수가 없는 문구를 1방향으로 단정하지 않습니다. 표시면 정보 충돌은 확인 필요로 표시하며 방향 수 충돌은 `--same-direction`을 켰을 때만 제외합니다. 원형 규격 원문도 보존하며 형상을 구분합니다.

재질·규격·용도·가격 점수 가중치는 `core/legacy_matching.py`의 `WEIGHTS`에 있습니다. 다만 기본 보강 비교는 이 가중합 하나로 정렬하지 않고, 구성 검사와 재질 우선순위를 먼저 적용합니다.

### 이전보다 경쟁사 칸이 적은 이유

`--limit 3`은 **기준 품목 3개**의 제한입니다. 경쟁사 칸이 줄었다면 후보 선정 조건을 확인해야 합니다.

현재 비교는 규격·가격 등의 필수 조건을 검사하고 정보 부족은 확인 필요, 일부 구성 차이는 대안 후보로 보충합니다. 방향 수는 선택 조건이며 용도 문구는 순위에만 반영합니다. 후보 풀은 품목당 최대 500건이므로 빈칸이 시장 전체에 경쟁품이 없다는 뜻은 아닙니다. 웹의 후보 검색·탈락 집계는 후보별 첫 탈락 사유와 상세 조회 수를 보여줍니다. 동일단가 재검색 시에는 마지막 검색의 집계입니다.

2026-10-23 지지대·10% 규격 검사 추가 전의 로컬 결과 대조에서는 동일한 기준 품목 3개에 대해 이전 비교표는 경쟁사 9개, 보강 비교표는 1개였습니다. 추가 API 조사에서 GK-ST08은 분류·재질·가격 조건을 통과한 14건 중 표시면 수 미확인 11건, 설치방식 차이 11건이 있었습니다. 두 집계는 중복됩니다. GK-HS03의 `안내판 산책길방향안내` 검색은 자기 상품 1건을 반환했습니다. 실행 시점·조회 조건에 따른 표본이며 현재 조건의 통과 건수나 고정 시장 통계가 아닙니다.

같은 날 지지대·10% 규격 검사 추가 전의 `--exact-price --fallback-band 0` 실행에서는 경쟁사 9개와 사진 12개를 생성했습니다. 현재 동일단가 모드에도 필수 검사를 적용하므로 이 과거 결과와 같은 후보 수를 보장하지 않습니다.

- 기준 품목을 늘리려면 `--limit 0` 또는 더 큰 한도를 사용합니다.
- 경쟁사 상한을 늘리려면 `--top`을 조정합니다. 유효 후보가 늘어나는 것은 보장하지 않습니다.
- 동일 가격에서 비교하려면 `--exact-price --fallback-band 0`을 사용합니다. 필수 구성·규격 검사는 유지합니다.
- 누락 값을 같다고 가정하지 않으며 확인 필요로 표시해 보충합니다. 명확히 다른 품목 분류·형상, 규격 범위 밖 후보는 보충하지 않습니다.

## 4. Excel에 들어가는 내용

업체별 시트 안에 기준 품목마다 비교 블록을 만듭니다. 각 블록에는 물품식별번호, 규격, 모델명, 재질 원문, 용도·표시면, 가격, 사진이 들어갑니다. 기준 업체 헤더는 노란색이며 경쟁사는 오른쪽에 배치됩니다.

- 사진은 해당 품목의 `imgSrc` 원본을 내려받아 삽입합니다. 이미지 파일을 바꿔 끼우거나 스크린샷·OCR로 재작성하지 않습니다.
- 표시 크기만 원본 비율에 맞춰 조정합니다. 원본에 업체 로고·워터마크가 있으면 그대로 포함됩니다. 워터마크 자동 검출·제거 기능은 없습니다.
- 이미지 URL이 없으면 `원천 이미지 미기재`, 다운로드·디코딩 실패 시 `(이미지 실패)`를 표시합니다.
- 정보가 없으면 일부 필드에 `원천 미기재`를 표시합니다. 용도 행에 지지대 개수 또는 미확인을 표시하고, 경쟁사 헤더에는 `비교 보류: … 미확인`이나 `조건 충족 후보 없음`을 표시합니다.
- 후보의 회사명 셀 메모에서 재질 일치 수준과 규격·가격 우선 조건 충족 여부를 확인합니다.
- 현재 가격 셀은 쉼표를 넣은 표시 문자열입니다. 자동 합계·수식용 숫자 셀이 아닙니다. 기본 추출 경로의 가격은 Decimal로 처리합니다.

목록정보시스템이 항상 더 큰 사진을 제공한다고 가정하지 않습니다. 앞선 표본에서는 쇼핑몰과 동일한 400×400 파일도 확인됐습니다.

## 5. DB 없이 목록만 수집하기

```sh
uv run nara collect --keyword "안내판" --limit 500 --workers 4 --out catalog-live.xlsx

uv run nara collect --keyword "안내판" --company "지피코리아" \
  --min-price 100000 --max-price 1000000 --limit 200 --workers 2 --out catalog-live.jsonl
```

| 옵션 | 기본값·범위 |
|---|---|
| `--limit` | 기본 1,000건, 허용 `1..10000` |
| `--workers` | 기본 4개, 허용 `1..4` |
| `--min-price`, `--max-price` | 생략하거나 두 값을 함께 지정 |
| `--out` | 필수. `.xlsx` 또는 `.jsonl` |

첫 페이지에서 검색 건수를 확인한 뒤 페이지당 최대 100건을 작업 하나로 나누어 프로세스 배치로 처리합니다. 프로세스들이 요청 시작 간격 1초를 공유하며 재시도에도 같은 제한을 적용합니다. 응답 대기는 겹칠 수 있지만 프로세스 수만큼 초당 요청 수를 늘리지 않습니다.

진행 로그 예시는 다음과 같습니다. 페이지·건수는 실제 검색 결과에 따라 달라집니다.

```text
수집중 [0/?] 첫 페이지 조회 중 | 프로세스 4개
수집중 [1/5] 페이지 완료 | 100/500건
수집중 [5/5] 페이지 완료 | 500/500건
저장중 | catalog-live.xlsx
수집 완료 | 500건 | catalog-live.xlsx (...바이트)
```

`collect`의 진행 로그는 stderr, 최종 결과 JSON은 stdout입니다. `> result.json`으로 실행 결과를 분리해 저장할 수 있습니다. 비교표 명령의 출력 형식은 이 JSON 계약과 다릅니다.

- XLSX: `수집정보`, `실시간품목` 시트. 이미지 URL을 담지만 사진은 다운로드하지 않습니다.
- JSONL: 첫 줄은 `kind=metadata`, 이후 줄은 `kind=item`인 원본 품목입니다.
- `matched_total`은 검색 결과 건수이고 `response_total`은 응답 최상위 건수입니다. 사이트에서 두 값이 다를 수 있습니다.
- 일부만 수집하면 `truncated=true`입니다. `source_snapshot_verified=false`이며 원천의 한 시점 완전성을 보증하지 않습니다.
- 건수 변동·짧은 페이지·중복이 감지되면 실패로 종료합니다. 기존 출력 파일을 덮어쓰지 않습니다.

각 명령은 한 번 조회해 파일을 만드는 작업입니다. 실행 후 사이트 가격이 바뀌어도 기존 Excel이 자동으로 갱신되지는 않습니다. 새 조회 결과가 필요하면 새 출력 파일명으로 다시 실행합니다.

## 6. 코드 구조와 데이터 흐름

```text
업체명 또는 품목등록결과.xls
  → 기준 품목 추출
  → CandidateProvider.search / enrich
      ├─ LiveProvider: 쇼핑몰 검색·필요한 상세 조회
      └─ SQLiteProvider: 지정한 진단 DB 읽기
  → core 속성·재질·규격 파싱 + 후보 선정(core/comparison.py)
  → build_report: 업체별 Excel·원본 사진 삽입
```

| 경로 | 책임 |
|---|---|
| `core/legacy_matching.py` | 비교용 DTO, 동적 속성 파싱, 단위·방향·충돌 처리, 점수 |
| `core/comparison.py` | 기준 품목 비교: 보류 판정, 구성 검사, 상세 보강 조율, 경쟁사 선정. 조회 인터페이스 `CandidateProvider` 정의 |
| `core/matching/normalization.py` | 재질 명칭·성분·등급 비교와 정규화 |
| `core/catalog_sources.py` | 소스 범위, 식별자, 쿼리·가격 계약 |
| `src/transport.py` | 공유 요청 제한과 최대 3회의 HTTP 시도 |
| `src/g2b_client.py` | 공개 검색 응답·상세 속성 조회 어댑터 |
| `src/catalog_provider.py` | 실시간·진단 SQLite 조회 어댑터 |
| `src/build_report.py` | Excel 배치·사진·출력 파일 생성 |
| `src/compare_file.py` | 비교 CLI와 업체별 처리 조율 |
| `src/format_convert.py` | 기존 XLS 입력·제출 양식 변환 |
| `src/live_collection.py` | DB 없는 페이지별 프로세스 수집 |
| `src/updater/` | 선택형 DB 갱신·이력·게시·Prefect 운영 |
| `src/matching/` | 별도의 목적별 shadow/auto·학습·평가 운영 |
| `test/` | 단위·HTTP·CLI·DB·워크북 통합 검증 |

도메인 규칙과 입출력 어댑터를 나누어 서비스로 분리할 수 있는 경계로 구성했습니다. 현재 기본 실행물은 로컬 CLI이며, 수집·판정·Excel을 독립 HTTP 마이크로서비스로 배포한 상태는 아닙니다.

루트의 `compare_file.py`, `build_report.py`, `format_convert.py` 등은 기존 실행 진입점입니다. 구현은 `core/`, `src/`에 있으며 새 기능을 위해 실행 스크립트를 추가할 필요가 없습니다. `build_report.py`도 현재는 동일한 비교 CLI로 연결되며 고정 예시 품목을 사용하지 않습니다.

원천은 사이트 화면이 사용하는 비공식 공개 조회 계약입니다.

| 조회·필드 | 용도 |
|---|---|
| `POST /gm/gms/gmsd/newShopUntySrchApi.do` | 검색·가격 범위·업체명·페이지 조회 |
| `POST /gm/gms/gmsf/GdsDtlInfo/selectPdctAtrbInfo.do` | 식별번호·분류번호에 따른 상세 속성 보강 |
| `pdctAtrbNm`, `pdctAtrbCdDtl`, `pdctAtrbCdDtlNm` | 동적 속성 정의와 표시 값 |
| `ctrtUprc`, `itemIdnfNo`, `dtlsPrnmNo` | 계약단가, 물품식별번호, 세부품명번호 |
| `mnftrEtpsNm`, `ctentUntyGrpNm`, `imgSrc` | 제조업체, 계약업체, 이미지 경로 |

대상 호스트는 `https://shop.g2b.go.kr`입니다. 다른 사이트의 API 키·DB 자격증명을 찾아 저장하는 구조가 아닙니다. 공식 오픈API와는 별개이며 사이트 개편 시 계약 재검증이 필요합니다.

## 7. 선택 기능과 Docker

기본 비교·실시간 수집은 기본 의존성만 사용합니다. 선택 기능은 extra로 지정합니다.

| extra | 사용 기능 |
|---|---|
| `analytics` | Parquet·DuckDB |
| `matching` | CPU 모델 학습·평가 |
| `orchestration` | Prefect·Redis 작업 조율 |

```sh
uv run --locked --extra matching nara-match --help
uv run --locked --extra analytics nara-catalog --help
```

진단 DB를 사용하는 비교는 `--catalog-db`, `--catalog-run`, 필요 시 `--allow-incomplete`를 사용합니다. 동일단가 검색에 지지대·규격 등 필수 검사를 적용하며 사진을 다운로드하지 않고 URL로 표시합니다. 운영 auto의 정본으로 사용하는 DB와 구별됩니다. 상세 명령은 [진단 수집 안내](docs/catalog-operations.md)를 확인하세요.

`shadow`·`auto`에는 게시 manifest, 목적·품목군 정책, 인증된 활성 release와 평가 자료가 필요합니다. `--company` 실시간 모드와 함께 사용할 수 없습니다. `suggest` Excel 생성 성공은 동등성 자동 확정이나 업무 정확도 인증을 뜻하지 않습니다. [자동 매칭 운영 안내](docs/auto-matching-operations.md)를 따릅니다.

DB 발행·이력·예약 갱신이 필요하면 선택형 Docker 스택을 사용합니다. 새 환경은 `docker/.env.example`에서 `docker/.env`를 만들고 해당 비밀번호를 설정합니다. 기존 `.env`와 볼륨을 덮어쓰지 않습니다.

```sh
docker compose up -d --build
docker compose ps -a
docker compose exec -T updater-worker python -m src.updater.cli status --json
docker compose down
```

루트 `compose.yaml`이 `docker/compose.yaml`을 포함합니다. Nginx·Prefect·PostgreSQL·Redis·업데이터 등 운영용 구성이며, 접속 주소는 `http://127.0.0.1:4200`입니다. 품목 데이터는 SQLite, PostgreSQL은 Prefect 실행 메타데이터 용도입니다.

**Docker 시작만으로 수집·발행이 완료되지 않습니다.** 원천 수집은 기본 비활성이며 `nara export`는 이미 게시된 운영 카탈로그를 내보내는 명령입니다. 실시간 비교표나 `collect`의 대체 명령이 아닙니다. 최초 운영 발행 전에는 `no_publication`이 정상적으로 발생할 수 있습니다. 수집 활성화·발행·복사 절차는 [Docker 안내](docker/README.md), [업데이터 운영 안내](docs/price-updater-operations.md)를 확인하세요.

이미 `docker/`에서 시작한 스택은 같은 위치·프로젝트 이름을 유지합니다. 루트에서 새로 시작하면 다른 Compose 프로젝트·볼륨을 사용할 수 있습니다.

## 8. 자주 발생하는 문제

| 현상 | 확인·조치 |
|---|---|
| 비교표 품목이 3개만 있음 | `--limit 3`을 사용한 테스트 결과. 전체는 `--limit 0` |
| 경쟁사 칸이 0~2개임 | `--top`은 상한. 규격·분류·형상·재질·가격 탈락 건수와 조회 범위 제한을 웹 검토의 후보 진단에서 확인 |
| `비교 보류: 지지대수 미확인` | 원천 속성과 상세 조회에 수량이 없는 상태. 사진 판독 API는 아직 연결되지 않았으며 미확인을 0개로 간주하지 않음 |
| `company_not_found` | 사이트의 제조업체명·계약업체명과 정규화 후 정확히 일치하는지 확인 |
| 출력 파일이 이미 있다는 오류 | 새 파일명 사용. 기존 결과는 유지됨 |
| 출력 경로 오류 | 비교표의 상위 폴더는 자동 생성. `.xlsx` 확장자·쓰기 권한·상위 경로에 같은 이름의 파일이 있는지 확인. `nara collect`는 폴더를 미리 생성 |
| `--fallback-band` 조합 오류 | 기본 비교에서는 0. 양수 가격대 재검색은 `--exact-price`와 함께 사용 |
| 이미지 미기재·실패 | 원천 URL 유무·응답·이미지 형식을 확인. 다른 품목 사진으로 대체하지 않음 |
| `no_publication` | 운영 DB에 첫 발행이 없는 상태. 실시간 업무는 `compare_file.py` 또는 `nara collect` 사용 |
| 수집 중 건수 변동·중복 오류 | 원천이 조회 도중 변경됐는지 확인하고 새 파일명으로 재실행 |
| 선택 패키지를 찾지 못함 | 해당 명령에 `--extra matching`, `--extra analytics`, `--extra orchestration` 적용 |

## 9. 검증 명령

기본 의존성으로 비교표·파서·조회 경계를 확인합니다.

```sh
uv run --locked python -m unittest \
  test.test_legacy_matching test.test_company_comparison \
  test.test_g2b_client test.test_catalog_client test.test_catalog_matching -q
```

선택 기능을 포함한 전체 테스트는 다음과 같습니다.

```sh
uv run --locked --all-extras python -m unittest discover -s test -t . -q
```

기본 테스트 실행은 fixture·로컬 HTTP 서버를 사용합니다. Docker 통합 검사는 명시적으로 활성화하는 별도 항목이며 기본 실행에서 건너뛸 수 있습니다. fixture의 통과율을 실제 업무 매칭 정확도로 해석하지 않습니다. 제품 코드에 타입 경고가 남아 있으므로 전체 정적 검사가 경고 없이 통과한다고 주장하지 않습니다.
