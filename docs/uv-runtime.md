# 터미널 실행 환경

Python 3.12와 uv를 사용한다. 저장소 루트의 `pyproject.toml`은 직접 의존성, `uv.lock`은 설치 버전과 패키지 해시를 고정한다. 현재는 DB 구축을 미루고 사이트를 직접 조회해 파일로 저장한다. Docker와 Prefect는 이 흐름에 필요하지 않다.

저장소 루트에서 설치하고 실행한다. `.venv`를 수동 생성하거나 활성화할 필요는 없다.

```sh
uv sync --locked
uv run nara --help
uv run python compare_file.py --company "지피코리아" --out comparison.xlsx
uv run nara collect --keyword "안내판" --limit 500 --workers 4 --out catalog-live.xlsx
```

입력 파일 없이 최종 비교표를 만들려면 `compare_file.py --company`를 사용한다.
기존 병렬 수집기로 해당 업체의 품목을 조회하고 g2b 필드 변환·경쟁사 매칭·엑셀 렌더링을
이어 실행한다. 기준 가격은 나라장터 등록 계약단가다. 기본 비교는 재질·용도·방향·표시면·설치 구성을
대조한다. 지지대 개수가 같고 가로·세로 각각 기준 대비 ±10% 이내인 후보만 선정한다.
기준보다 높은 가격에서 작은 규격을 우선 찾고, 선정된 경쟁사는 가격 오름차순으로 배치한다.
우리 업체와 경쟁사의 사진을 엑셀에 넣으며 사진 다운로드가 실패하면 해당 칸에 표시한다.
업체는 법인격·공백을 정규화한 이름이 일치하는 제조업체(제조업체가 없으면 계약업체)만 선택한다.

```sh
uv run python compare_file.py --company "지피코리아" --company "지피가든" \
  --keyword "안내판" --limit 3 --top 3 --workers 4 --out comparison-test.xlsx
```

업체마다 시트 하나를 만들고 그 안에 품목별 비교 블록을 넣는다. 지정한 업체들은 서로
경쟁사 후보에서 제외한다. `--keyword`는 기준 업체의 조회 품목을 제한한다.
`--limit`은 업체별 상한으로 0이면 전체, 1~10,000이면 해당 범위만 비교한다.
0일 때 검색 결과가 10,000건을 초과하면 일부를 전체처럼 내보내지 않고 오류로 종료한다.
업체 조회의 페이지당 프로세스 작업은 최대 4개이며, `--workers`는 경쟁사 매칭 스레드 수도 설정한다.
비교표의 `--out`은 `.xlsx` 경로이며 없는 상위 폴더는 자동 생성한다. 따옴표로 감싼 `~/Downloads/비교표.xlsx`도 지원한다.
기존 출력 파일을 덮어쓰지 않는다. 원본 `.xls`나 중간 `collect` 파일은 필요하지 않다.
비교 결과는 추천 후보이며 동등성 자동 확정이나 업무 정확도 인증을 뜻하지 않는다.

같은 가격에서 비교하려면 `--exact-price --fallback-band 0`을 추가한다.
이 경로도 지지대·규격 등 필수 구성 검사를 유지한다. `--exact-price`에서 `--fallback-band`를
생략하면 조건을 충족한 동일단가 후보가 없을 때 가격대를 넓힌다. 이때도 기준보다 높고 30% 상한 이내인 후보만 선정한다.
기본 비교에서는 근사 가격대 재검색을 하지 않는다.
`--limit`은 기준 품목 수, `--top`은 경쟁사 수의 상한이며 후보 개수를 보장하지 않는다.
상세 규칙과 후보가 줄어드는 원인은 [README](../README.md#3-기본-보강-비교-규칙)를 확인한다.

지지대 수는 0개와 미확인을 구분한다. 특정 업체·상품번호별 개수를 고정하지 않고 원천 속성과 규격명의 명시된 수량을 읽는다.
원천에 개수나 미포함이 명시되지 않으면 사진이나 지지대 높이로 추정하지 않는다.
기준 품목의 규격·지지대 수가 미확인이면 자동 비교를 보류하고 Excel 헤더와 터미널에 이유를 표시한다.
현재 사진에서 개수를 자동 판독하는 Vision API나 모델은 연결되어 있지 않다.

기존 파일 방식은 `uv run python compare_file.py INPUT.xls --out comparison.xlsx`로 유지한다.
이때는 입력 파일의 희망가를 사용한다. `--company`와 입력 파일은 동시에 지정할 수 없다.

`collect`는 실행 시점에 검색 조건으로 조회한다. 첫 페이지에서 검색 건수를 확인한 뒤 나머지 페이지를 배치로 처리한다. 페이지 하나가 작업 하나이며, 별도 프로세스가 HTTP 조회와 품목 파싱을 수행한다. 페이지당 100건, 프로세스는 기본 4개이고 `--workers 1..4`로 조절한다. 첫 페이지 이후 배치마다 최대 프로세스 수만큼 요청을 제출하며 결과는 페이지 순서로 합친다.

전체 프로세스가 요청 시작 간격 1초를 공유한다. 재시도 요청에도 같은 제한을 적용하고 서버의 재시도 대기시간을 공유한다. 병렬 처리로 응답 대기를 겹칠 수 있지만 초당 요청 수가 프로세스 수만큼 늘지는 않는다.

`--limit`은 기본 1,000건, 허용 범위 1~10,000건이다. 키워드·업체명·가격 범위를 함께 지정할 수 있으며 가격은 최솟값과 최댓값을 모두 입력한다. `.jsonl`로 저장하면 품목별 원본 필드도 보존한다.

```sh
uv run nara collect --keyword "안내판" --company "업체명" \
  --min-price 100000 --max-price 300000 --limit 200 --workers 2 --out catalog-live.jsonl
```

XLSX는 `수집정보`, `실시간품목` 시트로 구성된다. JSONL 첫 줄은 `kind=metadata`인 수집정보이며 이후 줄은 `kind=item`인 품목별 원본이다. 터미널에는 `수집중 [1/5] 페이지 완료 | 100/500건` 형식의 진행 로그와 저장·완료 상태를 stderr로 즉시 출력한다. 최종 수집 건수와 파일 크기의 JSON은 stdout으로 출력하므로 `> result.json`으로 저장해도 진행 로그가 섞이지 않는다. 두 형식 모두 검색 조건, 요청 한도, 실제 수집 건수, 검색 결과 건수(`matched_total`), 응답 최상위 건수(`response_total`), 수집 시작·종료 시점을 기록한다. 검색 결과 건수와 응답 최상위 건수는 사이트에서 서로 다를 수 있다.

한도 때문에 일부만 수집하면 `truncated=true`로 표시한다. 수집 중 건수 변동, 짧은 페이지 또는 품목 중복이 발견되면 오류로 종료하고 결과 파일을 만들지 않는다. 전체 결과를 같은 시점에 고정한 조회는 아니므로 `source_snapshot_verified=false`이며, 건수가 같은 상태에서 발생하는 원천 변경까지 보장하지 않는다. 이미지 파일은 내려받지 않는다.

출력 폴더는 미리 존재해야 하고 기존 파일은 덮어쓰지 않는다. 반복 실행할 때 새 파일명을 지정한다. 파일은 매번 새로 조회한 결과이며 자동 갱신·가격 변경 이력·운영 DB 발행은 수행하지 않는다. `--data-dir`도 이 명령에서 사용하지 않는다.

기존 `uv run nara sample --limit 100 --out catalog-test.xlsx`는 간단한 순차 테스트용으로 유지한다. 기본 비교 명령도 사이트 실시간 추천이며 `collect` 결과 파일을 자동으로 매칭에 연결하지는 않는다.

선택 기능은 다음 extra로 설치한다.

| extra | 기능 |
|---|---|
| `analytics` | Parquet·DuckDB |
| `matching` | CPU 모델 학습·평가 |
| `orchestration` | Prefect·Redis를 통한 기존 작업 조율 |

```sh
uv sync --locked --all-extras
uv run --all-extras nara-match --help
uv run --all-extras nara-catalog --help
uv run --all-extras python -m unittest discover -s test -t . -q
```

기존 DB 운영 기능을 선택하면 품목 저장소는 `sqlite3` 기반 SQLite 파일이고 Docker PostgreSQL은 Prefect 메타데이터 저장소이다. 기존 `refresh`는 `orchestration` extra와 Prefect 서비스가 필요한 별도 경로다. `collect`는 이 경로를 실행하지 않으며 DB 생성·이전·운영 데이터 마이그레이션을 수행하지 않는다. 기존 Docker 구성과 볼륨은 이후 운영 방식을 정할 때 사용할 수 있도록 유지한다.
