# Price updater operations

The updater publishes reconciled observations, not a source-guaranteed simultaneous market snapshot. Existing legacy crawl `done` markers are never refresh checkpoints. The default deployment is paused, its daily 02:00 Asia/Seoul schedule is inactive, the dispatcher is disabled, and production source access is disabled.

## Configuration and registration

On a new checkout, copy `docker/.env.example` to `docker/.env`, replace both credential placeholders and set permissions to 600. Start from the repository root with `docker compose up -d --build`. Root `compose.yaml` includes the complete definition in `docker/compose.yaml`; the included project loads `docker/.env` automatically. Nginx publishes only `127.0.0.1:4200` (or `PREFECT_HOST_PORT`); Prefect, PostgreSQL and Redis have no host-published ports. Use self-hosted Basic auth (`PREFECT_SERVER_API_AUTH_STRING` and client `PREFECT_API_AUTH_STRING`), never `PREFECT_API_KEY`. The browser uses relative `/api`. See [gateway and memory operations](gateway-operations.md).

The default startup automatically runs `updater-bootstrap` once and starts the worker/dispatcher only after registration succeeds. A new deployment is paused with its named daily schedule inactive. Repeated startup updates its packaged code location while preserving operator activation and schedules. Explicit re-registration is available with `docker compose run --rm updater-bootstrap`. The process worker runs code at `/app`, with limit one and no Docker socket. New deployment concurrency is one with CANCEL_NEW.

`python -m src.updater.cli refresh --mode full` submits through Prefect. It never calls the collector directly. Set `PREFECT_API_URL`, `PREFECT_API_AUTH_STRING`, and `NARA_DATA_DIR` for host invocations. For a manual first collection, set `NARA_SOURCE_ENABLED=true`, recreate the worker and leave `NARA_DISPATCH_ENABLED=false`. The CLI rejects disabled source access before enqueueing. For recurring collection, additionally enable the dispatcher and activate the deployment and named schedule using Prefect.

Default full collection probes pages beyond the former 1,000-row safety threshold, the midpoint and the final page. It rejects short, repeated, overlapping or count-mismatched probes. It then persists one unfiltered scope and divides page work into chunks of at most ten pages, with four tasks in flight and a shared request-start budget of one per second. This avoids splitting prices and handles large groups of identically priced products. Every collected page still checks counts, unique item keys, fingerprints and expected length; final reconciliation and the 12-hour observation limit remain mandatory. An explicit `NARA_PRICE_DOMAIN_JSON` still selects the original Decimal price partition strategy using `lower`, `upper`, `quantum`, and `max_partition_rows`; its single-price overflow remains unresolved.

The dispatcher checks the latest due slot every 30 seconds. Its slot key is independent of enqueue attempts. A lost enqueue response is retried with the same Prefect idempotency key. A cancelled precollection dispatch can receive at most three recovery attempts after 30/60/120 seconds. Once collection begins, automatic immediate resubmission stops. `refresh --retry-slot SLOT_KEY` is an explicit operator retry of the persisted business run; a new fencing token verifies the profile, original parent snapshot, age and stored collection policy. Runs over 12 hours require a fresh run.

## Data and diagnostics

`status --json` includes source/dispatcher activation, run attempts, maintenance state, source observation window, information groups and last successful refresh time. When a stage exists, `collection_progress` reports expected/collected items and expected/completed pages. `current`, `history LISTING_KEY`, `history LISTING_KEY --price-only`, `catalog-manifest --out PATH`, and `export --out PATH.xlsx` read published data. Excel includes current items, field changes, and price history; timestamps identify Asia/Seoul and all source text remains literal. Warning starts after 36 hours and stale after 72 hours, measured from source observations rather than maintenance publication time.

Large original page responses are retained losslessly as gzip BLOB values in the existing stage `pages.raw_json` column; smaller responses remain text. SQLite's existing non-strict column accepts both. Decode BLOB values with `gzip.decompress(value).decode()` before parsing; row evidence and operational snapshots keep their existing JSON contracts. No previous page evidence is rewritten. See [live capacity measurements](collection-capacity.md) for initial size estimates; neither images nor future history growth is included.

Collection tasks carry bounded page chunks, persist each page with its checkpoint, and retry transient failures once. HTTP transport attempts at most three calls, so an unsuccessfully retried page has at most six HTTP attempts. Flow retries and publication retries are zero. Prefect receives only compact summaries. A publication event, active pointer and scheduled-slot success commit in one SQLite transaction. A failure to acknowledge afterward cannot undo committed data.

## Maintenance, backup and restore

Use `src.updater.maintenance.enter_maintenance(Store())` before a maintenance operation. The persistent `control/maintenance.flag` stops new bootstrap, dispatcher, worker collection and production matching readers. When a Prefect API is configured, native scheduling is paused and every schedule made inactive. Existing pinned readers finish. Keep this flag across service restarts.

`backup(store, destination)` copies control with SQLite Online Backup and all extant event-referenced immutable snapshot files, including retained rollback versions, checking their SHA256. This is the business backup. Take a separate PostgreSQL dump using `pg_dump -U prefect prefect` inside this Compose project's postgres service and store the dump securely. Neither command should dump credentials or container environments into evidence.

`restore(store, backup_path)` validates the bundle, enters maintenance, and refuses to replace files while any snapshot pin is held. It leaves the gate active. Validate published queries, history and hashes after restoration. Matching ledger, model, calibrator and vocabulary recovery is a separate coordinated operation; this module does not modify those artifacts. Only after those checks should an operator call `resume(store)`. Resume removes the business gate; it does not reactivate schedules or enable the dispatcher.

`prune_files` retains the newest three publication snapshots, every current pointer, and all pinned versions. Terminal stages expire after seven days. `prune_history` publishes a new maintenance snapshot for 365-day history retention, retaining current versions, the boundary baseline and all referenced versions/evidence. It preserves source refresh identity, observation windows, checked/changed times and slot success. Immutable files are never edited in place. Publication tombstones remain in control after snapshot deletion.

Disk preflight uses measured stage/snapshot bytes, three-copy allowance and 20% headroom with a minimum 2 GiB free space. Large production runs still need a measured sample of at most 1,000 rows and an approved full-scope estimate. Current sample measurements do not certify production capacity.

## Isolated QA and cleanup

QA uses project `nara-updater-qa`, loopback port 14200, separate named volumes and `docker/compose.fixture.yaml`. Execute `NARA_QA_ENV_FILE=/protected/qa.env NARA_STACK_QA=1 .venv/bin/python -m unittest test.integration.test_price_updater_stack -v` only after starting that project. It never calls the live source. Stop only this project's created services using `docker compose -p nara-updater-qa ... down` without `--volumes`; retain fixture volumes and evidence. Host reboot and Docker daemon restart are not performed by this QA and require separate operational acceptance.
